# Как достать файлы с диска Synology, когда сам NAS умер

У меня сдох DS723+. Диск целый, данные на нём, а прочитать их нечем: воткнул
в компьютер — система предлагает отформатировать. Ни Mac, ни Windows такой
диск не понимают, а второго Synology под рукой нет.

Здесь описано, как я всё-таки добрался до файлов, и лежат инструменты, чтобы
вы повторили это у себя. Всё работает **только на чтение** — диск не
изменяется ни на байт.

## Почему диск не читается

Synology не кладёт файлы на диск напрямую. Между ними три слоя:

```
раздел на диске
   └── MD RAID          ← собирается даже когда диск ОДИН
         └── LVM         ← логические тома
              └── btrfs  ← а вот и файлы
```

Каждый слой сам по себе понятен Linux. Проблема в другом: **Synology
использует собственный флаг в заголовке btrfs**, которого нет в обычном ядре.
Обычный Linux видит его, считает файловую систему повреждённой и отказывается
монтировать. Именно на этом обычно всё и заканчивается — даже у тех, кто
добрался до нужного слоя.

Лечится это правкой одной строки в ядре. Об этом ниже.

## Что здесь лежит

| файл | зачем |
|---|---|
| `syno_offset.py` | сам находит, где на диске начинается файловая система |
| `nbd_server.py` | отдаёт нужный кусок диска по сети, только на чтение |
| `lima-cloud-config.yaml` | настройки виртуальной машины для macOS |

## Порядок действий

### Шаг 1. Подключите диск и найдите раздел

Диск из NAS ставится в USB-корпус для 3.5 дюймов. Важно: **корпус должен быть
с отдельным питанием** — от одного USB большой диск не запустится, будет
щёлкать и отваливаться.

Смотрим, какие разделы появились:

```bash
diskutil list          # macOS
lsblk                  # Linux
```

Разделов от Synology будет три. Нужен **самый большой** — остальные это
подкачка и система DSM.

### Шаг 2. Узнайте смещение

```bash
sudo python3 syno_offset.py /dev/disk4s5
```

Скрипт прочитает служебные заголовки и посчитает всё сам:

```
MD RAID: версия 1.2, уровень 1
  служебная область: 2048 секторов = 1048576 байт

LVM: группа томов «vg1»
  первый экстент начинается на секторе 1152
  размер экстента: 8192 секторов (4 МБ)
  том «volume_1»: 5719296 экстентов, начинается с экстента 3

ПРОВЕРЯЮ, ГДЕ ЛЕЖИТ ФАЙЛОВАЯ СИСТЕМА
  «volume_1»: смещение 14221312 — btrfs НАЙДЕНА

СМЕЩЕНИЕ: 14221312 байт
```

Цифры у вас будут свои — они зависят от модели и от того, как собран том.
Не переписывайте мои.

### Шаг 3. Дальше — по вашей системе

Файловую систему умеет читать только Linux, поэтому дальше всё зависит от
того, за каким компьютером вы сидите.

---

## Если у вас Windows

Самый короткий путь, потому что Windows умеет отдавать физический диск в
свою встроенную подсистему Linux целиком.

**1. Поставьте WSL2**, если ещё нет:

```powershell
wsl --install
wsl --update
```

**2. Найдите номер диска.** В PowerShell от администратора:

```powershell
wmic diskdrive list brief
```

Запомните строку вида `\\.\PHYSICALDRIVE2` — она нужна дальше.

**3. Пробросьте диск в Linux целиком:**

```powershell
wsl --mount \\.\PHYSICALDRIVE2 --bare
```

Ключ `--bare` важен: он отдаёт диск как есть, не пытаясь его смонтировать.

**4. Внутри WSL соберите слои:**

```bash
sudo apt update
sudo apt install -y mdadm lvm2 btrfs-progs

sudo mdadm --assemble --scan --run     # соберёт RAID даже из одного диска
sudo vgchange -ay                       # включит тома LVM
sudo lvs                                # покажет, что нашлось
```

**5. Попробуйте смонтировать:**

```bash
sudo mkdir -p /mnt/nas
sudo mount -o ro /dev/vg1/volume_1 /mnt/nas
```

Если смонтировалось — вам повезло, забирайте файлы. Они будут видны и из
Windows по адресу `\\wsl$\Ubuntu\mnt\nas`.

Если получили ошибку про `unsupported root flag` или «couldn't mount because
of unsupported optional features» — это тот самый проприетарный флаг Synology.
Переходите к разделу «Патч ядра».

> **Про диски из RAID на несколько дисков.** Если в NAS стояло два диска и
> больше, подключать нужно все и пробрасывать каждый: `wsl --mount` для
> каждого физического диска. `mdadm --assemble --scan` соберёт массив
> обратно. С одним диском из зеркала (RAID 1) тоже получится — массив
> запустится в неполном состоянии, данные будут целы.

## Если у вас macOS

Здесь сложнее: macOS не умеет пробрасывать диск в виртуальную машину так,
как Windows. Поэтому диск отдаётся в виртуалку по сети — для этого и написан
`nbd_server.py`.

**1. Поставьте Lima** (лёгкие виртуалки Linux):

```bash
brew install lima
```

**2. Запустите отдачу диска.** В отдельном окне терминала:

```bash
sudo python3 nbd_server.py /dev/disk4s5 14221312 0 10809
```

Числа — те, что выдал `syno_offset.py`. Ноль вместо размера означает «до
конца диска». Окно не закрывайте, пока не заберёте файлы.

**3. Поднимите виртуалку:**

```bash
limactl start --name=nas-reader lima-cloud-config.yaml --tty=false
limactl shell nas-reader
```

**4. Внутри виртуалки подключитесь к диску:**

```bash
sudo apt update
sudo apt install -y nbd-client btrfs-progs lvm2

sudo nbd-client 192.168.5.2 10809 /dev/nbd0
sudo mount -t btrfs -o ro /dev/nbd0 /mnt/nas
```

Адрес `192.168.5.2` — это ваш Mac со стороны виртуалки, у Lima он всегда
такой.

Если монтирование ругнулось на неизвестный флаг — идите в «Патч ядра».

## Если у вас Linux

Самый простой случай — всё нужное уже есть:

```bash
sudo apt install -y mdadm lvm2 btrfs-progs
sudo mdadm --assemble --scan --run
sudo vgchange -ay
sudo mount -o ro /dev/vg1/volume_1 /mnt/nas
```

При ошибке про флаг — следующий раздел.

---

## Патч ядра: главная часть

Вот та самая правка, без которой ничего не выйдет. Synology ставит в
заголовке файловой системы свой флаг — бит 34. Обычное ядро о нём не знает и
считает такую систему испорченной.

Мы разрешаем ядру этот флаг игнорировать. На чтение это совершенно
безопасно: флаг относится к внутренним возможностям Synology, а сами данные
лежат в обычном btrfs.

```bash
# Исходники ядра ровно той версии, что запущена
sudo apt install -y linux-source linux-headers-$(uname -r) build-essential \
                    flex bison libelf-dev libssl-dev

cd /tmp
sudo tar xf /usr/src/linux-source-*.tar.bz2 linux-source-*/fs/btrfs/

# Разрешаем флаг Synology (бит 34)
sudo sed -i 's/const u64 valid_root_flags = BTRFS_ROOT_SUBVOL_RDONLY |/const u64 valid_root_flags = BTRFS_ROOT_SUBVOL_RDONLY | (1ULL << 34) |/' \
    /tmp/linux-source-*/fs/btrfs/tree-checker.c

# Собираем модуль
sudo make -C /lib/modules/$(uname -r)/build M=/tmp/linux-source-*/fs/btrfs modules -j4

# Подменяем модуль на свой
sudo umount /mnt/nas 2>/dev/null
sudo rmmod btrfs
sudo insmod /tmp/linux-source-*/fs/btrfs/btrfs.ko

# И пробуем снова
sudo mount -t btrfs -o ro /dev/nbd0 /mnt/nas
```

**Грабли, на которых теряют вечер.** Собирать нужно именно через
`/lib/modules/$(uname -r)/build`, а не из распакованного дерева исходников.
Если собрать неправильно, версия модуля не совпадёт с версией ядра, и вместо
понятной ошибки вы получите падение системы без объяснений.

## Забираем файлы

Данные Synology разложены так:

```
/mnt/nas/
  homes/        — домашние папки пользователей
  Documents/    — и другие общие папки, как вы их называли
  @appdata/     — данные установленных пакетов
  @database/    — базы данных
  @docker/      — тома Docker
```

Копируем с продолжением при обрыве:

```bash
rsync -av --progress /mnt/nas/homes/ /куда/сохраняем/
```

**Про скорость.** Через USB 3.0 и сетевую отдачу выходит около 500 КБ/с — это
медленно, гигабайт идёт минут двадцать. Если данных много, копируйте
частями и начните с самого важного. На Windows через прямой проброс диска
получается заметно быстрее, там сети между слоями нет.

## Когда не сработало

**`syno_offset.py` не нашёл MD RAID.** Скорее всего выбран не тот раздел.
У Synology их три, нужен самый большой. Посмотрите `diskutil list` ещё раз.

**Нашёл LVM, но btrfs нигде нет.** Два варианта. Либо том зашифрован — тогда
нужен пароль и `cryptsetup`. Либо файловая система не btrfs, а ext4: старые
модели Synology и режим Basic используют её. Тогда монтируйте как
`mount -t ext4 -o ro`, патч ядра при этом не нужен.

**Массив не собирается, `mdadm` пишет про недостающие диски.** Если в NAS
было несколько дисков, подключите все. При RAID 1 хватит и одного, но
запустить массив придётся вручную: `sudo mdadm --assemble --run /dev/md0
/dev/sdb3`.

**Монтируется, но часть файлов не читается.** Значит на диске есть
повреждения. Добавьте к `rsync` ключ `--ignore-errors` и копируйте что
получится, а список сбойных файлов сохраните — потом станет ясно, что
потеряно.

## Важное про безопасность данных

Всё описанное — только чтение. `nbd_server.py` открывает диск в режиме
`O_RDONLY` и отклоняет любые попытки записи, монтирование идёт с ключом
`-o ro`. Это сделано намеренно: пока данные не спасены, диск лучше не
трогать вообще.

**Не запускайте на этом диске восстановление файловых систем** (`btrfs check
--repair`, `fsck` и подобное), пока не скопировали данные. Такие инструменты
пишут на диск и способны добить то, что ещё читается.
